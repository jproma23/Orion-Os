# ARQUITETURA — ORION OS

Regras de arquitetura e convencoes do ORION OS. Todo modulo novo segue o que
está aqui.
**Leia este arquivo antes de qualquer implementação.**

## O que é o projeto

ORION OS é uma plataforma de robótica modular, **offline-first**: tudo que
mantém o robô seguro roda local, e a IA da conversa é remota, por API
(EDR-0021). O primeiro robô é o **Fofão**.

**Divisão de máquinas vigente: EDR-0036 (30/09/2026).** Ela substitui a da
EDR-0019 e a aposentadoria do Notebook de 09/09.

| Unidade | Papel | Hardware | Linguagem |
|---|---|---|---|
| Vision Core + Voice Core | YOLO, rostos, palavra de ativação, Whisper, chamadas da IA, Piper. **Só processa, não guarda estado** | Notebook 8 GB (Debian) + webcam USB + alto-falante USB | Python 3.13 |
| Mission Core | Memória, recados, GOAP, decisões: **o dono do estado** | Raspberry Pi 4 (4 GB) + SSD | Python 3.13 |
| Motion Core | Navegação, LiDAR, fusão de sensores, ponte com o corpo, banco no SSD, interface web | Raspberry Pi 4 | Python 3.13 |
| Hardware Core (corpo) | Tempo real: motores, servos, bússola, segurança reativa | ESP32-D0WD-V3 (DevKit), desde 02/08 (o Arduino Mega morreu) | C++ (PlatformIO) |
| Ouvidos | 2 microfones I2S, fala direto com o Notebook (TCP 9100) | ESP32 | C++ |
| ~~Rosto~~ | ~~Olhos, boca, toque~~ — **a tela SAIU do robô em 25/10/2026** (dono); o rosto voltou ao avatar do Notebook | ~~ESP32-S3 (tela 3,5")~~ | — |

> Core está desligado no Pi e roda dentro do `orion-avatar` do Notebook, com
> código de 19/08. Ver a seção "Estado em 25/10" da EDR-0036.

## Regras arquiteturais invioláveis

1. **Toda comunicação entre módulos passa pelo Event Bus.** Nenhum módulo
   importa ou chama outro diretamente. (Cap 6)
2. **Notebook ↔ corpo: proibido.** A cadeia é Notebook —TCP— Raspberry
   —Serial— ESP32 do corpo. Só o Raspberry fala com o corpo. (Cap 3, 5;
   EDR-0018) O ESP32 dos **ouvidos** não é o corpo e fala direto com o
   Notebook (EDR-0036).
3. **O corpo (ESP32) nunca executa IA nem navegação**; apenas comandos simples
   (MOVE_FORWARD, MOVE_DISTANCE, TURN_LEFT, STOP, DOCK...) e segurança
   reativa. Toda a lógica de controle dos motores fica encapsulada nele.
   (Cap 10)
4. **Visão e voz rodam no Notebook** (`src/orion/vision/`, `src/orion/voice/`);
   Mission Core, navegação, banco de dados e interface web rodam no
   Raspberry, com dados no SSD. O Notebook manda ao Pi só eventos, nunca
   vídeo nem áudio. (Caps 8, 9, 12, 13, 15; EDR-0036)
5. **Nenhum módulo abre o SQLite diretamente** — só via API de memória /
   Database Manager (que roda no Raspberry; o Notebook consulta via
   TCP). O banco vive no SSD, nunca no cartão SD. (Cap 11, 15)
   Backup diário com réplica cruzada Raspberry ↔ Notebook.
6. **Nenhum valor fixo no código** — todo parâmetro vem de `config/orion.yaml`
   via Configuration Manager. (Cap 17)
7. **Segurança em 3 camadas**: reativa no corpo/ESP32 (nunca depende dos
   demais), tática e estratégica no Raspberry. **Se o Notebook sumir, o robô
   fica parado, seguro e avisando** (EDR-0036). Em dúvida,
   parar. (Cap 18)
8. **Todo COMMAND no protocolo exige ACK**; mensagens têm id, versão,
   timestamp e CRC — mesmo formato no TCP e no Serial. (Cap 5, 14)
9. Um módulo = uma responsabilidade. Logs estruturados em tudo.

## Comandos

```bash
# Ambiente (as duas máquinas: Pi e Notebook)
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

# Rodar o sistema
python -m orion                      # boot completo (Cap 6, seção 4)
python -m orion --sim                # com Raspberry/corpo simulados

# Testes
pytest tests/unit -q                 # unitários (rodar após TODA mudança)
pytest tests/integration -q -m sim   # integração com simuladores

# Firmware
cd firmware/hardware_core && pio run          # compilar
# gravar no ESP32 (no Pi): o reset automático NÃO funciona nesta montagem.
# Segurar BOOT, parar o orion-motion, gravar com esptool --no-stub --baud
# 115200 na porta /dev/serial/by-id/... e depois tirar e pôr o USB.
```

## Convenções de código

- Python: type hints obrigatórios, `ruff` para lint, docstrings em português.
- Eventos nomeados em inglês minúsculo com ponto: `motion.obstacle_front`,
  `vision.person_detected` (lista oficial nos Caps 5–16).
- Mensagens do protocolo: JSON compacto conforme Cap 5 seção 5 — o mesmo
  formato nos enlaces TCP (Notebook↔Raspberry) e Serial (Raspberry↔ESP32 do corpo).
- Commits: `[modulo] descrição` (ex.: `[kernel] event bus com prioridades`).
- Todo bug corrigido ganha teste de regressão (Cap 19).
- Firmware: máquina de estados do Cap 10 seção 4; nunca bloquear o loop
  principal (sem `delay()` em código de produção).

## Fluxo de trabalho (decidido em 2026-07-27)

Toda mudança de código segue este ciclo, nesta ordem. Nada vai para o
`master` sem passar pelas sete etapas:

```
Problema → Análise → Implementação → Testes unitários →
Testes no hardware → Documentação → Commit
```

1. **Problema** — o que está quebrado ou faltando, com evidência (log,
   comportamento observado), não suposição.
2. **Análise** — ler o código relevante antes de mexer; entender a causa
   antes de propor a correção.
3. **Implementação** — um arquivo por vez (ver "Protocolo de integração"
   abaixo); nenhuma resolução de conflito ou mudança sem compilar/rodar
   os testes em seguida.
4. **Testes unitários** — cobrindo o problema original (regra já existente:
   "todo bug corrigido ganha teste de regressão"). Rodar a suíte inteira,
   não só o arquivo tocado.
5. **Testes no hardware** — validação física no Pi/ESP32/robô de verdade.
   Testes unitários provam que o código faz o que foi escrito para fazer;
   só o hardware prova que o que foi escrito resolve o problema físico.
   **Uma correção sem este passo é "em validação", não "pronta"** — ver
   o mapa de saúde abaixo.
6. **Documentação** — `docs/journal.md` (o que mudou e por quê) e, se for
   decisão de arquitetura, um EDR novo em `docs/edr/`.
7. **Commit** — mensagem no formato `[modulo] descrição`, com o raciocínio
   no corpo. Só depois disto o código está pronto para o `master`.

### Mapa de saúde dos módulos

Todo módulo do projeto é classificado em uma de quatro categorias (🟢🟡🟠🔴),
mantidas em `docs/ESTADO_DOS_MODULOS.md`. O critério de classificação não é
opinião de sessão — é a Rubrica abaixo, que é a única fonte de verdade sobre
o que cada cor significa.

## Rubrica do Mapa de Saúde do ORION

Anexo de processo. Define o critério **único** de classificação de status
dos módulos — preenche o mapa contra um padrão fixo, em vez de improvisar o
critério a cada sessão. (Decidida em 2026-07-27, junto com o Fluxo de
trabalho acima.)

### Invariante

**Status é uma afirmação sobre evidência, não sobre intenção.**

Nenhum módulo recebe cor sem que a evidência que justifica a cor esteja
anexada na mesma linha (suíte de teste, commit ou log de hardware, com
data). Uma célula sem evidência datada **não tem status** — marca-se `?` e
trata-se como pendência de verificação, não como verde por omissão.

Isto existe por uma razão medida: o journal listava "3 bugs ALTOS abertos"
que já estavam todos corrigidos. Status marcado uma vez e nunca reconferido
apodrece. A rubrica é o antídoto.

### Os quatro estados — condições de entrada estritas

Cada cor tem uma condição objetiva e checável. Não há "quase lá".

| Cor | Nome | Condição de entrada (todas obrigatórias) |
|---|---|---|
| 🟢 | Estável | Testes unitários passam **E** validado no hardware físico **E** data da validação de hardware presente na linha. |
| 🟡 | Em validação | Testes unitários passam. Hardware **não** validado (ou validação vencida). |
| 🟠 | Em desenvolvimento | Funciona parcialmente. Testes incompletos, falhando, ou ausentes. |
| 🔴 | Pendente | Stub vazio, não implementado, ou quebrado. |

**A regra que segura tudo:** 🟢 exige log de hardware com data. Testes
passando são condição necessária, nunca suficiente. Código que só passou em
teste unitário é 🟡, não 🟢 — porque a odometria é malha aberta e a única
checagem de realidade do robô é o hardware rodando.

### Teto atual do projeto

**O teto CAIU em 2026-07-29**, e este parágrafo era a razão de o mapa inteiro
estar preso em amarelo. O robô se moveu por decisão própria: log de produção
com "IA decidiu explorar" seguido de "segmento de 30 cm concluido"; e em
2026-07-30 o dono viu o relé dos TB6600 acionar em modo autônomo — a cadeia
decisão → navegação → serial → firmware → energia está provada ponta a ponta.

Isso NÃO promove ninguém a 🟢 automaticamente. A rubrica não mudou: 🟢 exige
validação de hardware **datada, na linha do módulo**. O que mudou é que o
gate deixou de ser impossível — antes nenhum módulo PODIA ser verde; agora
quem tiver a evidência datada pode. Continua valendo a regra de rebaixamento
1: qualquer commit que toca o módulo derruba o status para `?`.

Ressalva de 30/07 (HISTÓRICA - ver a atualização logo abaixo): **deslocamento
físico ainda não foi medido.** Os motores estão desconectados (só os drivers
TB6600 no robô, rodas suspensas) e não há encoder de roda — a odometria conta
passos COMANDADOS, não medidos.

> **Atualização (auditoria C6-09, 12/11/2026):** o motor de passo e os TB6600
> saíram. Desde 13/09 os motores são DC com encoder, numa ponte L298N
> (`firmware/hardware_core/include/pins.h`), e desde 31/10 a odometria conta
> pulsos MEDIDOS do encoder (`fusao_sensores.py`, `origem: encoder`). O encoder
> mede a RODA, não o chão: roda no ar ainda "anda" - quem confere o chão é o
> LiDAR, e desde 12/11 a câmera testemunha o giro (`odometria_visual.py`).

### Formato obrigatório da tabela

Toda linha carrega estas colunas. Nenhuma é opcional.

| Módulo | Status | Últ. verificação | Evidência | Gate faltante |
|---|---|---|---|---|
| `motion_core/behavior` | 🟡 | 2026-07-27 | 439 testes, commit `6b8815e` | validação no hardware |
| `src/orion/memory` | 🔴 | 2026-07-27 | stub vazio (removido) | implementação |

- **Últ. verificação:** data em que a evidência foi conferida NESTA sessão.
  Não é a data em que o código foi escrito — é a data em que se olhou.
- **Evidência:** o que sustenta a cor. Suíte + nº de testes, ou commit, ou
  referência ao log de hardware. Sem isto, a linha é `?`.
- **Gate faltante:** para tudo que não é 🟢, qual o próximo gate a cumprir.
  Célula 🟢 é a única que pode deixar esta coluna vazia.

### Regras de rebaixamento automático

O mapa não é um carimbo permanente. Um módulo **perde cor** quando:

1. **O código mudou desde a última verificação.** Qualquer commit que toca
   o módulo invalida o status anterior — volta para `?` até nova
   conferência. Verde não sobrevive a um diff não reconferido.
2. **A validação de hardware venceu.** Uma validação de hardware vale
   enquanto o hardware relevante e o código do módulo não mudam. Trocou
   fiação, driver, ou o próprio módulo → o 🟢 cai para 🟡.
3. **A evidência não pode ser reproduzida.** Se a suíte citada não passa
   mais, ou o log referenciado não existe, a cor é inválida na hora.

Rebaixamento é automático e não precisa de justificativa. Promoção precisa
de evidência nova e datada. **Não há promoção por opinião** — um módulo só
muda de status quando atende aos critérios da rubrica, nunca porque
"parece pronto". Regressão também é automática: se surgir um bug crítico,
um módulo pode voltar de 🟢 para 🟡 ou 🟠 na mesma sessão em que o bug foi
achado. A classificação deve ser **rastreável** — sempre que possível, com
referência a testes, EDRs, commits ou validações em hardware que a
justifiquem. **O mapa representa o estado atual do projeto, não o objetivo
desejado.**

### Procedimento de marcação

1. Antes de marcar qualquer módulo, **conferir no código** o estado real —
   não confiar no journal, no relatório, nem no status anterior do mapa.
2. Rodar (ou localizar na sessão) a evidência que sustenta a cor
   pretendida.
3. Preencher as cinco colunas. Se faltar evidência, marcar `?` e listar o
   módulo como pendência de verificação — nunca deduzir a cor.
4. Nenhuma célula 🟢 sem data de hardware. Na dúvida entre duas cores,
   escolher a **mais baixa**.

### Relação com o fluxo de desenvolvimento

As cores mapeiam os gates do ciclo formalizado acima:

```
Problema → Análise → Implementação → Testes unitários → Testes no hardware → Documentação → Commit
                                     └──── 🟠 vira 🟡 ────┘ └──── 🟡 vira 🟢 ────┘
```

- Passar do gate de **testes unitários** move 🟠 → 🟡.
- Passar do gate de **testes no hardware** move 🟡 → 🟢.

O gate de hardware foi a fronteira intransponível até 2026-07-29, quando o
robô passou a se mover por decisão própria. Ele continua sendo a fronteira
entre amarelo e verde — o que mudou é que agora dá para atravessá-la, com
evidência datada por módulo (ver "Teto atual do projeto" acima).

## Ordem de implementação

Siga `docs/historico/PLANO_IMPLEMENTACAO.md`. Resumo: Fase 0 (esqueleto) → Fase 1 (Kernel +
Event Bus) → Fase 2 (Comunicação TCP + Serial + firmware básico) → Fase 3
(Banco/Memória) → Fase 4 (Hardware Core completo) → Fase 5 (Vision no
Notebook) → Fase 6 (Voz + IA) → Fase 7 (Motion Core/Navegação no Raspberry +
autocalibração) → Fase 8 (Avatar + interface web) → Fase 9 (Diagnóstico/Segurança) →
Fase 10 (validação Cap 19).

**Não avance de fase sem os testes da fase atual passando.**
